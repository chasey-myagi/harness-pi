Architecture comparison · Agent Core 设计理念对比

harness-pi × pi-mono — "Hook 作为一等公民" 到底不一样在哪

harness-pi 的 @harness-pi/core 故意没有基于上游 @earendil-works/pi-agent-core（pi-mono monorepo 的一部分）—— 它自己重写了一个 agent loop，换来的是「hook 作为一等公民」。这句话经常被当成营销用语一带而过， 这份报告把它拆开：两边的 loop 实际怎么写、扩展点长什么样、事件怎么流、tool 怎么并发、状态怎么持久化—— 逐项对代码，再回答两个更难的问题：pi-mono 有什么设计得比我们好，我们有什么设计得比它好，以及为什么。

OVERVIEW · 先说结论

一句话结论：两边都叫"可扩展"，但扩展的是不同的东西

pi-mono 的 @earendil-works/pi-agent-core 优化的是「一个干净、状态管理正确、事件流忠实的单 agent loop」， 可扩展性是**追加**的——先有能跑的 loop，再在它外面套一层可选的 AgentHarness 拿到持久化和一个真正的多监听器 hook 总线， 再往上 coding-agent 又搭了第三套、完全独立的 Extension 系统给终端 UI 用。三层各自为政，没有一个类型贯穿始终。

harness-pi 反过来：先设计一个**贯穿内核到插件的单一 Hook 接口**（四种精确的执行语义：event / decision / transform / around）， 再把 loop 写成"围绕这个接口派发"的壳。代价是内核比 pi-agent-core 的 agent-loop.ts 复杂（自估 400-600 LOC 的额外重写成本）， 换来的是 decision hook 可以真正拦截（deny / modify / abort），而不只是"事后收到通知"。

核心差异一句话 pi-mono 把"可扩展"理解成 observer（观察者，看得到但改不了） + 若干具名单槽位回调； harness-pi 把"可扩展"理解成 interceptor（拦截器，能否决、能改写、能注入、能中止）， 并且四种语义（并行观察 / 顺序拦截 / 链式改写 / 嵌套包裹）被显式建模、显式合并、显式失败语义化——而不是揉成一个"谁先返回非空谁赢"的黑盒。

但这不等于"harness-pi 全面更好"。pi-mono 在会话数据模型（可分支的 session 树 vs 线性 append-only 日志）和 分层可选复杂度（想要极简 loop 就不用背负 hook 派发的心智负担）上有真实的、值得借鉴的设计。后文会展开。

ARCHITECTURE · 一张图看懂分裂在哪

harness-pi：一个接口贯穿三层 vs pi-mono：三层各自一套机制

两边都是"三层"，但"三层共享什么"完全不同。harness-pi 的 Controller / Plugin / Kernel 三层共享同一个 Hook 类型—— 一个 plugin 作者写一个对象字面量，同时实现 onPreToolUse（decision）和 onTurnEnd（event）毫无障碍， 因为两者都是同一个 Hook 接口上的字段。pi-mono 的三层——agent-loop.ts/Agent、 AgentHarness、coding-agent 的 Extension——是三套互不知情的机制： 写一个 AgentHarness hook 用的类型和写一个 coding-agent extension 用的类型没有任何共同祖先。

这张图直接回答"hook 作为一等公民"这句话具体指什么：不是"有没有 hook"，是"hook 是不是贯穿整个系统的单一心智模型"。 pi-mono 三层里，只有中间的 AgentHarness 有真正的拦截能力（block/patch），而且这一层是可选的—— 直接用最底层的 Agent/agentLoop（pi-agent-core 的对外主入口）完全不知道"hook"这个概念， 只有几个具名单槽位回调。harness-pi 反过来，从 AgentSession 内核往上到最外层 Controller， 每一层说的都是同一种语言：一个 Hook 对象。

HARNESS-PI · 深挖内核

"一等公民"具体落地：一个 Hook 接口，四种执行语义

packages/core/src/hook.ts:460-622 定义的 Hook 接口，字段按方法名前缀分成四组， HookDispatcher 按前缀路由到四种不同的执行策略——这是整个"一等公民"说法的技术落点： 

export interface Hook {
  name: string;                    // 调试/metrics/log 归因，必须唯一
  timeout?: number;                // per-hook 超时(ms)：event 默认100 / decision 200 / pipe 500
  internal?: boolean;              // 内部 hook 不上报 metric
  requires?: string[];             // 硬依赖：缺失/顺序错 → warn，不阻塞
  prefers?: string[];              // 软依赖：有更好，无 warning
  conflictsWith?: string[];        // 声明冲突：同时存在 → warn
  failClosed?: boolean;            // 仅 decision hook：超时/抛错时 true=deny，false(默认)=fail-open
  critical?: boolean;              // 安全关键 hook：强制显式声明 failClosed，否则构造期直接 throw

  // ── Event：Promise.all 并行，纯观察 + 注入 ──
  onSessionStart?(input, ctx): HookResult | void | Promise<...>;
  onTurnStart?(input, ctx): HookResult | void | Promise<...>;
  onTurnEnd?(input, ctx): HookResult | void | Promise<...>;
  onLlmEnd?(input, ctx): HookResult | void | Promise<...>;
  onContextOverflow?(input, ctx): HookResult | void | Promise<...>;
  onAfterFlush?(input, ctx): OnAfterFlushResult | void | Promise<...>;  // collect-return
  onPostToolUse?(input, ctx): HookResult | void | Promise<...>;
  onContinuationCheck?(input, ctx): HookResult | void | Promise<...>;
  onSessionEnd?(input, ctx): HookResult | void | Promise<...>;
  onError?(input, ctx): void | Promise<void>;
  onSubagentStart?(input, ctx): void | Promise<void>;
  onSubagentEnd?(input, ctx): void | Promise<void>;
  onSteer?(input, ctx): HookResult | void | Promise<...>;

  // ── Decision：顺序 await，可 short-circuit ──
  onPreToolUse?(input, ctx): HookResult | void | Promise<...>;
  onUserPromptSubmit?(input, ctx): HookResult | void | Promise<...>;

  // ── Transform：顺序 pipe，链式改写 ──
  transformSystemPromptBeforeLlm?(systemPrompt, ctx): string | void | Promise<...>;
  transformMessagesBeforeLlm?(messages, ctx): Message[] | void | Promise<...>;
  transformToolsBeforeLlm?(tools, ctx): Tool[] | void | Promise<...>;

  // ── Around：嵌套洋葱，reduceRight 构造 ──
  wrapTurn?(ctx, next: () => Promise<void>): Promise<void>;
  wrapToolExec?(call, ctx, next: () => Promise<ToolExecResult>): Promise<ToolExecResult>;
}

四种形态共用一个统一返回 envelope（hook.ts:255-279），dispatcher 负责解释里面的字段，hook 本身不直接调用任何"deny()"之类的命令式 API：

export interface HookResult {
  continue?: boolean;                       // false → 结束 session（任一 false 即 false）
  stopReason?: string;
  decision?: "allow" | "deny";              // 仅 decision hook；首个给出即赢
  reason?: string;
  updatedInput?: Record<string, unknown>;   // 改 tool 参数（last-writer-wins）
  updatedToolOutput?: ToolExecResult;        // 改 tool 结果（last-writer-wins）
  additionalContext?: string;                // 拼成 attachment，按注册顺序累积，非决断字段
  systemMessage?: string;                    // 给用户 console，不进 LLM context
}

构造期安全校验：不许安全关键 hook "忘了表态"

assertCriticalDecisionHooks（dispatcher.ts:637）在 session 构造时强制校验： 任何标了 critical:true 的 hook 必须是 decision hook，且必须显式声明 failClosed——否则直接 throw，拒绝构造。 这堵的是一类真实会发生的事故：一个本该"超时/抛错就拒绝放行"的安全 hook，因为作者忘了想清楚失败路径， 默默 fail-open 放过了本该被拦下的调用，而且不会有任何报错提示你漏掉了这一步。

两个真实 hook 实现

// packages/plugins/src/watchdog.ts — Around 形态
export function watchdog(opts: WatchdogOptions): Hook {
  return {
    name: "watchdog",
    async wrapTurn(ctx, next) {
      const timer = setTimeout(() => {
        opts.onTimeout?.(ctx, ctx.turnIdx);
        ctx.abort(`watchdog: turn ${ctx.turnIdx} timed out after ${opts.turnTimeoutMs}ms`);
      }, opts.turnTimeoutMs);
      try { await next(); } finally { clearTimeout(timer); }
    },
  };
}
// packages/plugins/src/token-budget.ts — Event 组合：注入 + 停止决策两阶段
export function tokenBudget(opts: TokenBudgetOptions): Hook {
  return {
    name: "token-budget",
    prefers: ["cost-tracker"],  // 有更精确的 token 来源就用，没有就自累计
    onTurnStart(input, ctx) {
      return { additionalContext: renderBudgetStatus(ctx) }; // 每 turn 持续反馈剩余百分比
    },
    onTurnEnd(input, ctx) {
      if (budgetExhausted(ctx) || diminishingReturns(ctx)) {
        return { continue: false, stopReason: "token-budget-exhausted" };
      }
    },
  };
}

两个例子分别展示 around 和 event 两种形态的真实写法：watchdog 用 next() 包裹整个 turn 体， 借协作式 ctx.abort() 而不是硬 timeout race 来终止——around hook 之所以不套 per-hook timeout （dispatcher.ts:389 注释原话：next() 就是整个 turn/tool exec，时长本就合法可变， "太久"该由协作式 abort 判断，而不是外部 race-timeout 硬杀）。tokenBudget 展示了同一个 hook 对象 如何同时挂两个不同的 event 方法，一个负责"持续提醒"，一个负责"最终拍板"，互不干扰。

协作面被收窄到 ctx.state

Plugin 之间禁止互相 import，协作只能经过 HookContext.state——一个用 TypeScript module augmentation 注册 key 类型的共享 map。repeatedCallGuard.ts 是个例子： 

declare module "@harness-pi/core" {
  interface HookStateRegistry {
    "repeated-call-guard:window": Map<string, number>;
  }
}

这条纪律（连同上面的 requires/prefers/conflictsWith 三个依赖声明字段） 是"Hook 一等公民"里容易被忽略的一半：不仅是"能不能拦截"，也是"多个 plugin 同时存在时，协作面有没有被明确约束"。

PI-MONO · 深挖 agent-core

pi-mono 的可扩展性：三层，三套互不相通的机制

Layer 1 — agent-loop.ts / Agent：具名单槽位回调，没有通用 hook 概念

AgentLoopConfig（packages/agent/src/types.ts:140-282）是最底层 agentLoop() 的配置对象。关键点：每个扩展点是一个单独的可选函数字段，不是可注册的数组/Set。想让"日志"“预算控制”“watchdog” 三个关注点同时挂在 beforeToolCall 上，调用方必须自己手写一个函数顺序调用三者、手动合并 block/reason 结果——loop 内核不提供任何组合/编排能力： 

export interface AgentLoopConfig extends SimpleStreamOptions {
  model: Model<any>;
  convertToLlm: (messages: AgentMessage[]) => Message[] | Promise<Message[]>;   // 必需
  transformContext?: (messages, signal?) => Promise<AgentMessage[]>;
  shouldStopAfterTurn?: (context: ShouldStopAfterTurnContext) => boolean | Promise<boolean>;
  prepareNextTurn?: (context: PrepareNextTurnContext) => AgentLoopTurnUpdate | undefined | Promise<...>;
  getSteeringMessages?: () => Promise<AgentMessage[]>;
  getFollowUpMessages?: () => Promise<AgentMessage[]>;
  toolExecution?: "sequential" | "parallel";      // 默认 "parallel"
  beforeToolCall?: (context: BeforeToolCallContext, signal?) => Promise<BeforeToolCallResult | undefined>;
  afterToolCall?: (context: AfterToolCallContext, signal?) => Promise<AfterToolCallResult | undefined>;
}

每个字段的 TSDoc 都强调"契约稳定性"（Contract: must not throw or reject...）——这是 pi-mono 的另一种设计取向： 与其让 dispatcher 处理复杂的失败语义，不如约定"你这个函数不许抛错"，把复杂度推给调用方自律。 Agent 类（agent.ts）把这些同名单槽位字段原样存成 this.beforeToolCall 等 public 字段， 依然是单槽位，没有升级成列表。

Agent 另外提供一个真正的多监听器机制，但只用于只读事件通知，没有拦截能力： 

// agent.ts:173, 241-244

subscribe(listener) { this.listeners.add(listener); return () => this.listeners.delete(listener); }

processEvents() 先用事件更新内部 state，再顺序 await 每个 listener——listener 拿不到"拦截/修改"能力，纯观察者模式。

Layer 2 — AgentHarness：一个真正的多监听器 hook 总线，但只存在于这一可选层

AgentHarness（harness/agent-harness.ts，1029 行）是包在 Agent/agentLoop 外面的可选封装，内置 session 持久化、compaction、branch summarization、skills。它自己实现了一个按事件类型分桶、 每类可挂多个 handler 的总线——pi-mono 内部确实用"hook"这个词指代它（AgentHarnessErrorCode 里有 "hook" 分类）： 

private handlers = new Map<string, Set<AgentHarnessHandler>>();

on(type, handler) {
  let hs = this.handlers.get(type);
  if (!hs) { hs = new Set(); this.handlers.set(type, hs); }
  hs.add(handler);
  return () => hs.delete(handler);
}

private async emitHook(event) {
  const handlers = this.getHandlers(event.type);
  if (!handlers?.size) return undefined;
  let lastResult;
  for (const handler of handlers) {
    const result = await handler(event);
    if (result !== undefined) lastResult = result;   // ⚠️ 后一个非 undefined 结果覆盖前一个，不是合并
  }
  return lastResult;
}

19 种事件类型里（harness/types.ts:634-656），只有一部分携带可拦截的 result：

事件能做什么
before_agent_start注入额外 messages / 覆盖 systemPrompt
context替换整个 messages 数组（≈ harness-pi 的 transformContext，但走同一条总线）
tool_callblock + reason（≈ onPreToolUse）
tool_resultpatch content/details/isError/terminate（≈ onPostToolUse）
session_before_compact / session_before_tree取消或提供自定义 compaction/摘要结果
其余 12 种（model_update、queue_update、abort 等）只读通知，无 result

createLoopConfig()（agent-harness.ts:399-448）展示了 Layer 2 如何"喂"回 Layer 1 的单槽位接口——用一个 lambda 把 emitHook 的 fan-out 结果适配成 Layer 1 期待的单一函数： 

beforeToolCall: async ({ toolCall, args }) => {
  const result = await this.emitHook({ type: "tool_call", toolCallId: toolCall.id, toolName: toolCall.name, input: args });
  return result ? { block: result.block, reason: result.reason } : undefined;
},

也就是说：多个 AgentHarness hook 想同时判定"要不要 block 这次工具调用"，靠的是 emitHook 里那个 "最后一个非 undefined 结果覆盖前面"的规则——如果 hook A 想放行、hook B 想拦截，谁在 Set 里后注册谁说了算， 没有短路、没有优先级、没有冲突告警。这是唯一有拦截能力的地方，也是合并语义最粗放的地方。

Layer 3 — coding-agent 的 Extension 系统：第三套、独立的插件机制

packages/coding-agent/src/core/extensions/types.ts 开篇注释："Extensions are TypeScript modules that can: Subscribe to agent lifecycle events / Register LLM-callable tools / Register commands, keyboard shortcuts, and CLI flags / Interact with the user via UI primitives"。这是给终端 CLI 产品（pi 命令）的用户写自定义扩展用的， 类型定义引用 TUI/Theme/Overlay* 等 UI 类型，由 ExtensionRunner （extensions/runner.ts:263）+ createExtensionAPI() （extensions/loader.ts:213）驱动。这一层与 AgentHarness.on() 完全独立—— 两者都能叫"扩展/hook"，但接口、事件类型、生命周期不共享任何祖先。

值得注意的是，pi-mono 根目录和 packages/agent/README.md 都没有类似 harness-pi docs/00-07 那种专门论述"扩展性设计取舍"的架构文档——agent 包的自我描述重心是 "state management + event streaming + AgentMessage 抽象（让应用能塞自定义消息类型）"， 可扩展性不是这个包被设计出来时的核心叙事。

TURN LOOP · 逐步对齐执行顺序

同一件事，两种写法：一轮 LLM + Tool 循环

harness-pi 的 AgentSession 把一轮 turn 拆成 _phaseLlmCall → _phaseToolBatch → _phaseTurnEnd 三个显式方法，每个 phase 边界都是一个 hook 注入点。pi-mono 的 agentLoop() 只有一个扁平 while 循环 （packages/agent/src/agent-loop.ts:155-269），阶段划分是隐式的代码块，没有对外暴露"phase"概念—— 扩展点是散落在循环体里的具名单槽位回调调用，而不是统一派发。

两边在"progress 事件里 message_update 是渐进式 partial 快照，message_end/onLlmEnd 才是权威终态"这条原则上是一致的——但 harness-pi 把这条原则做成了两套独立类型（下节展开）， pi-mono 只用一套 AgentEvent 类型表达。另外要指出的一个精度差异：pi-mono 的 beforeToolCall/ afterToolCall 是单函数，而不是 harness-pi 的 onPreToolUse/onPostToolUse 那样 可以同时挂多个 hook——这解释了为什么"多个关注点组合"在 pi-mono Layer 1 完全没有内置支持，必须手写胶水函数。

一个容易忽略的反向差异：默认值方向相反 harness-pi 的 isConcurrencySafe() 默认 false（保守：不声明安全就当不安全，出错也 fail-closed 为 unsafe）。 pi-mono 的 toolExecution 默认 "parallel"（乐观：不声明 sequential 就当可以并行）。 也就是说面对"新写的、忘了声明并发属性的工具"，harness-pi 会保守地把它当成屏障（慢但安全）， pi-mono 会乐观地把它并进去（快但如果这个工具其实有副作用冲突，问题不会在类型层面被拦下来）。

EVENTS · 给调用方看到的是什么

双轨类型系统 vs 单一类型的两条通路

两边都同意一条原则：message_update 是回合进行中逐块推送的 partial 快照，只有 message_end （harness-pi）/ 同名字段（pi-mono）才是权威终态，不能拿中间态当结果用。分歧在于：这条原则要不要反映到类型系统里。

harness-pi 明确排除 decision/pipe/around 类 hook 的输出进入 recorded 轨（session.ts:35-41 注释： decision 能改控制流、pipe 是 plugin-to-plugin 转换链、around 是嵌套语义，三者都跟"只读 flat event 流"不兼容）。 这个区分在真实场景里有价值：如果要把 recorded 轨接到审计/重放系统，pi-mono 的 AgentEvent 里混着大量 "这轮还没完成、可能被后续 delta 覆盖"的中间态，不加过滤直接落盘会有噪音；harness-pi 从类型层面就先把这两种用途分开了。

PERSISTENCE · 会话状态存成什么形状

线性 append-only 日志 vs 可分支的 session 树

这是本报告里 pi-mono 数据模型明显更丰富的一处。harness-pi 的 SessionStore 是单一线性日志， pi-mono 的 AgentHarness session 是可在任意历史节点 fork 的树。两者服务的场景不同，细节见下。

pi-mono 的 SessionStorage（getLeafId/setLeafId/appendEntry/getPathToRoot/findEntries） 支持在历史任意节点开新分支而不用复制之前的全部消息——这是终端交互产品的刚需（/rewind、比较两种续写方向）。 compaction、branch summarization 也内置在这一层（harness/compaction/*），通过 session_before_compact 等 hook 事件可被外部拦截/自定义，但默认实现就在包内——不像 harness-pi 把 compaction 完全移出内核， 变成 @harness-pi/plugins 里独立的 compactOnOverflow/CompactRestartFresh/CompactResumeFromBoundary controller。

反过来，harness-pi 这套线性 HWM 模型换来的是一个更强的一致性保证：strictPersistence 模式明确定义了 "落盘不全时该怎么对外报告"（提级为 error），这条规则在 pi-mono 的研究里没有找到对等物—— SessionStorage.appendEntry 是否具备幂等重试语义，需要看具体 jsonl-storage.ts 实现， 在接口/类型层面没有像 strictPersistence 这样被显式建模和文档化。

WHERE PI-MONO WINS · 客观地说，这几处它做得更好

pi-mono 有什么设计得比 harness-pi 更好

"harness-pi 的 hook 更强大"不等于"harness-pi 全面更优"。以下三点是 pi-mono 真实占优、且理由能立住的设计。

① Session 树 vs 线性日志——原生支持 rewind / 分支

AgentHarness 的 session 存储是一棵可在任意历史节点 fork() 的树（parentId 链）， harness-pi 是单一线性 append-only 日志。想要"从对话中间某一点开一条新的续写、同时保留原来那条"， pi-mono 原生支持，且不需要复制之前的全部消息；harness-pi 要做等价的事，只能靠 forkSession controller 整份复制父 session 的内存快照，产生一个全新的、脱离原持久化链条的独立 session。

为什么更好：对交互式产品（/rewind、比较两种续写方向、A/B 探索同一个上下文）来说， 树模型是原生匹配的数据结构；线性模型要么不支持，要么只能用"整份复制"这种更重的机制模拟。harness-pi 目前不需要这个能力 （批处理 worker 场景下极少有人要"回到第 5 轮重新走一条分支"），但如果未来要做交互式产品线，这是需要补的一块。

② 分层可选复杂度——最简单的场景不用背 hook 派发的心智负担

pi-mono 把"我只要一个能跑的 LLM+tool 循环"（agentLoop()）和"我要持久化+hook 总线"（AgentHarness） 拆成两个独立可选的层。只用最底层的消费者完全不需要学习任何"hook"概念，只要填几个具名回调字段。 harness-pi 的 AgentSession 把 4 态 HookDispatcher 焊死在内核里——即便你的插件列表是空的， 每一次 turn 依然会走一遍 event/decision/transform/around 四条派发路径。

为什么更好：不是所有消费者都需要拦截能力。pi-coding-agent 本身是个跑在生产环境、 被大量用户使用的真实产品，证明了"没有通用 hook 系统"这条路径本身就足以支撑一个成熟产品——复杂度应该按需引入， 而不是让每个使用者都为最强大的那 20% 场景付学习成本。这是"渐进暴露复杂度"和"统一心智模型"两种设计哲学的真实权衡， pi-mono 选了前者。

③ 契约稳定性优先——"不许抛错"比"复杂的失败语义"更好记

AgentLoopConfig 每个回调字段的 TSDoc 都写明 Contract: must not throw or reject。 harness-pi 用 failClosed/critical/per-method 默认超时（100/200/500ms）来表达"这个 hook 失败了该怎么办"， 规则数量和组合方式明显更多。

为什么更好：对单人或小团队维护的项目，"函数不许抛错，出错自己兜底"是一条几乎不会被记错的规则； harness-pi 那套失败语义组合（谁 fail-open、谁 fail-closed、超时多久、critical 校验何时触发）需要写文档、需要新人专门学习。 规则越少，越不容易被写错——这也是一种正确的简单性，不能因为"功能更少"就简单认定它更差。

次要的一点（证据不如上面三条厚，值得未来单独深挖）：pi-mono 的 AgentMessage 是可扩展的消息类型抽象， 设计目的是让不同的上层应用往同一条 message 时间线里塞自定义消息种类。harness-pi 的扩展性集中在行为/控制流层面 （能不能拦截、能不能改写），没有在数据模型层面提供类似"自定义消息类型"的一等公民机制——如果 harness-pi 的下游应用 需要往 transcript 里塞非标准消息种类，目前只能通过 attachment/additionalContext 这类旁路手段。

WHERE HARNESS-PI WINS · 这几处是真实工程教训换来的

harness-pi 有什么设计得比 pi-mono 更好

这几条不是"功能更多所以更好"，而是每一条都能指向一个具体会出错的场景，以及为什么现在的机制能堵住它。

① 拦截能力贯穿全层，而不是锁在一个可选层里

pi-mono 唯一能拦截（block/patch）的地方是 AgentHarness 的 19 种事件里的 5 种， 而 AgentHarness 本身是可选的——直接用 Agent/agentLoop（大多数嵌入式集成的实际入口） 完全没有这个能力，只有具名单槽位回调。harness-pi 的拦截能力在 AgentSession 内核里， 任何消费者、任何层级都拿得到同一套 onPreToolUse/onUserPromptSubmit。

为什么更好：harness-pi 文档里记的具体场景是 bidding-agent 的 lease 冲突拦截—— 多个 worker 竞争同一个 lease，必须在 tool 真正执行之前否决掉。这类需求只要消费方选择了"轻量"入口就做不到， 等于说"能不能拦截"变成了一个前期架构选型问题，而不是随时可以加上的能力。

② 精确的分场景合并语义，而不是"最后写的赢"

pi-mono 的 emitHook：多个 handler 都返回结果时，最后一个非 undefined 的覆盖前面所有的—— 没有短路、没有优先级、没有冲突告警。harness-pi 对四种形态分别定义合并规则， 其中一条特别值得复述：decision hook 的决断字段（decision/continue）首个赢， 但非决断字段（additionalContext/systemMessage）不算决断，会照样累积 （dispatcher.ts:217）。

为什么更好：这条规则是刻意设计出来防一个具体 bug 的——如果一个"只是想注入点上下文"的 hook 的输出被当成决断值处理，会误屏蔽掉后面本该生效的安全检查的 deny。pi-mono 的"最后非 undefined 赢"规则下， 这种误屏蔽是真实会发生的：两个 hook 同时想 patch tool_result.content，后注册的会静默覆盖前一个，没有任何提示。

③ 构造期强制校验：安全关键 hook 不许"忘了表态"

assertCriticalDecisionHooks 在 session 构造时检查：任何 critical:true 的 hook 必须显式声明 failClosed，否则直接 throw，拒绝构造。pi-mono 的研究没有发现任何等价的 "强制显式声明失败语义"机制。

为什么更好：这类校验堵的是"写代码时最容易漏掉、出问题时最难排查"的一类 bug—— 一个本该 fail-closed 的安全检查，因为作者忘了处理超时/异常路径，默默 fail-open 放行了本该被拒绝的请求， 而且不会有任何编译期或启动期的提示。把这类错误从"运行时才发现（甚至发现不了）"提前到"构造期直接崩溃"， 是一种低成本、高杠杆的正确性投资。

④ collect-return：从真实数据损坏事故里改出来的持久化写入模式

harness-pi 的 onAfterFlush 被设计成"hook 只能返回数据，内核负责实际落盘"，而不是给 hook 一个可以自己调用的异步写接口。文档记录了这是从真实 bug 重新设计的结果：上一版给 hook 一个 detached 的 appendCompactionBoundary 回调，超时 hook 的写操作仍在飞，乱序落在 terminal 之后， resume 时被误当"丢弃之前一切"。

为什么更好：这不是纸面上的架构洁癖，是一条从生产事故里长出来的具体设计纪律—— "涉及持久化的 hook 接口，绝不能让 hook 自己持有写句柄"。pi-mono 目前没有等价的、被明确记录下来的设计讨论； 如果 AgentHarness 未来允许 hook 异步写 session 树，这类竞态是潜在风险点。

还有三条分量稍轻、但同样有具体场景支撑的差异，合并陈述：

  • 双轨事件系统——把"给 UI 抖动看的中间态"和"给审计/重放用的权威轨"从类型层面分开， recorded 轨天然排除了 decision/pipe/around 类会影响控制流的 hook 输出。pi-mono 的单一 AgentEvent 两条通路推同一份数据，想做审计重放的消费方得自己在运行时过滤中间态。
  • 段级并发屏障——保留模型撰写的调用顺序，只在 unsafe 调用处切一刀，比"整批只要有一个 sequential 就全降级" 的并行度更高（尤其是长批次、少量 unsafe 调用穿插在中间的场景）。代价是实现更复杂，见 § Tool 并发对比末尾的默认值反向差异。
  • 协作纪律——ctx.state 收窄协作面 + requires/prefers/conflictsWith 依赖声明，在构造期就能发现"这个 hook 需要另一个 hook 但没装"这类配置错误。pi-mono 的 AgentHarness.on() 没有等价的声明机制，多个 handler 之间的顺序完全依赖 Set 插入顺序这一隐式约定。

CONCLUSION · 设计哲学的本质差异

不是"谁的 hook 更多"，是"扩展性被优化给了谁"

pi-mono 把复杂度控制权交给消费者：想要多简单就多简单（裸 agentLoop），想要多强大就自己往上叠 （AgentHarness，再往上 Extension）。这是一种"渐进暴露"的哲学，正确地服务了它的主场景—— 一个需要被大量第三方以不同深度集成的通用库，不应该强迫每个集成者都先理解一套四态派发引擎。

harness-pi 把复杂度前置到内核设计者身上：先想清楚"生产 harness 到底需要哪些精确的拦截/合并/失败语义"， 把这些一次性焊进 Hook 接口，换来的是每一个插件作者面对的都是同一套、已经被想清楚边界条件的模型。 这是一种"统一心智模型"的哲学，正确地服务了它的主场景——一个自己维护全部插件生态、需要 lease 拦截/审计重放/ 构造期安全校验这类生产级保证的服务端 worker 运行时。

如果只能记住一句话 pi-mono 问的是"我能不能观察到这件事发生了"，答案在裸 Agent 层是"能，但改不了"， 在 AgentHarness 层是"能，还能改，但改的时候大家一起抢"。harness-pi 问的是 "谁有权决定这件事要不要发生、发生的时候允许被谁以什么顺序改"，并且把这个问题的答案——四种执行语义、 失败时怎么办、多个答案冲突时听谁的——都做成了类型系统和构造期校验能检查的东西，而不是留给运行时"随缘"。

两条路径都不是"更先进"，是针对不同主场景做的不同押注。harness-pi 现在最值得从 pi-mono 身上补的一课， 是会话数据模型不必被迫是线性的——如果未来 harness-pi 要支持任何形式的"探索式多分支"场景 （比如 sub-agent 结果比较、同一上下文多个候选续写），线性 SessionStore + 整体复制式 forkSession 会是第一个需要重新设计的地方。

DEEP DIVE ① ② · SESSION DATA MODEL

持久化演进与 sideQuestion：先修正一个集体错觉

第一部分把这个议题表述为"线性 log vs 可分支树"。实读代码后这个表述需要修正： harness-pi 的存储数据模型已经是树形的——每条 entry 带 parentId（session-store.ts:71）、 读取靠从 leaf 沿 parentId 回溯、getPathToLeaf 本就接受任意历史 leafId 参数 （session-store.ts:80），接口注释里明写"未来可分叉成树"（session-store.ts:12）。 所以真正的争论不是数据模型之争，而是 API 原语之争：要不要暴露"移动 leaf"。

三个真实的坏结果（严重度递增排序反转：第一个今天就存在）

  • 无 rewind，且有一个现存 footgun：resume() 硬编码从当前 leaf 重建（session.ts:1107）。 如果调用方绕开它、自己用 getPathToLeaf(sessionId, oldLeaf) 重建历史再 continue()， 后续 append 仍会挂到当前 leaf 之后——内存历史与落盘 lineage 从此静默错位。协议暴露了"按历史 leaf 读"， 内核却没有配套的"按历史 leaf 写"。
  • fork 存储放大：store.fork() 的语义是批量复制前缀（session-store.ts:85-88）。 150-turn（约 1000 条 entry）的父 session 派 8 个探索分支 = Postgres 里多 8000 行纯重复数据。 gap-explorer / maker-verifier 这类 fan-out 模式规模一上来就会疼。
  • 无 checkpoint 重试：leaseQueue 的重试是整 item 从零重跑；turn 40/50 失败的 work item 要重付 40 turn 的 token。

对照修正另一个认知：pi-mono 的分支其实是单活跃分支的 rewind 模型（moveTo(entryId) 把 leaf 指回历史节点）， 而且它的 JSONL 落盘里 leaf 移动本身就是一条 append-only 的 "leaf" entry、重放时推导—— "可变 leaf"完全可以用 append-only 实现，与 harness-pi 的 HWM 哲学不冲突。

议题 ① 裁决 现在不实现 A / B / C′ 任何一个；把 B + C′ 写进设计文档作为既定演进路径并绑定触发条件。 唯一近期动作是零成本的：在 session-store.ts / resume() 文档里明令 "按历史 leafId 读出的路径不可用于续写"，把 footgun 从"静默数据污染"降级为"文档禁令"。 期权不会过期，不必现在行权。

议题 ②：sideQuestion——deferred controller 深挖出一个现存缺陷

sideQuestion（docs/06 §7.1，唯一未落地的 controller）能找到的最强场景： lark-bot 挂着一个跑到 turn 60、上下文 120k token 的服务端 run，运营在群里问"它现在验证到哪一步了"。 逐项排除现有原语——steer() 会把问题注入正式对话（污染历史、改变模型后续行为）； subAgentTool 是模型驱动的，运营触发不了；forkSession 功能上可用但成本上是坏的—— 而排查"为什么成本坏"时挖出了一个比 sideQuestion 本身更要紧的问题：

现存缺陷：getCacheSafeParams() 与 live 投影不一致 autoCompaction 活跃时，父 session 发给 LLM 的是 [boundary.summary, …slice(coveredCount)] 投影 （session.ts:1287-1296，特意复用同一 summary 对象保 prefix bytes 稳定）； 而 getCacheSafeParams() 返回的是全量 _messages（session.ts:476-486）。 fork 出的"cache-safe"子 session 首个请求前缀与父完全不同 → 必然 cache miss、全价 120k input。 它也不携带 llmOptions——而 pi-ai 的 StreamOptions.sessionId 正是 provider 侧 session 级缓存的钥匙。 名字承诺的 cache-safe，在压缩场景下不成立。

三个候选设计里，"turn 边界注入 + 回答后回滚 _messages"被直接否决（HWM 依赖 append-only 绝不 splice， 回滚会让 _persistedCount 指向不存在的索引）；"内核内联 session.ask()"要绕开 _running 互斥、 打穿 live 事件严格配对契约、污染有状态 pipe hook——为未证实的需求往最重的文件里加并发路径，违背内核极简。 胜出的是薄 recipe 方案：controller 只是 forkSession 之上约 60 行的组装 （无 tools、maxTurns:1、不传 store、不挂 hooks），内核侧唯一要动的是把快照接缝修对： 

// 内核侧唯一改动：快照按 live 投影导出，并携带复现 cache key 所需的一切
getCacheSafeParams(): {
  systemPrompt: string;
  forkContextMessages: Message[];   // ← _activeBoundary 投影后的 view，且过滤 incomplete toolCalls
  model: Model<Api>;
  llmOptions: LlmOptions;           // ← 含 sessionId / cacheRetention / providerExtras(thinking)
}
议题 ② 裁决 controller 本体继续 defer（维持 roadmap 判断——"非它不可"的调用方目前只有 lark-bot 一个候选）； 但 getCacheSafeParams() 的投影修正提前做。这不是为 sideQuestion 投机：它修正的是现有公开 API 的名不副实 （forkSession 用户今天就会在 autoCompaction 场景吃到全价 cache miss），改动小、可测， 并顺手把未来 sideQuestion 的全部内核前置条件清零——真需求来时，落地只是 plugins 层 60 行 recipe。

// core 新增（~50 行）：slot 是值不是字符串——变量传递不丢类型，
// 跨 plugin 共享从"约定同一个字符串"升级为"import 同一个 slot 对象"（pnpm why 可查）
interface StateSlot<T> {
  readonly key: string;            // 物理 map key 仍是 string（调试/序列化友好，运行时零变化）
  readonly owner: string;          // 诊断归因
  readonly validate?: (v: unknown) => v is T;  // dev-mode 运行时校验，F2 类脏写在写入点当场抓住
}
export function defineSlot<T>(key: string, opts: {...}): StateSlot<T>;

// TypedStateMap 加 overload，string 老路保留、标 @deprecated 渐退：
get<T>(slot: StateSlot<T>): T | undefined;
set<T>(slot: StateSlot<T>, value: T): void;

// deferred-tools.ts 只改一行导出形态：
export const ACTIVATED_SLOT = defineSlot<Set<string>>("deferred.activated", { owner: "deferredTools" });

F1 随之解决（batch-counter 在工厂闭包里 defineSlot<number>(动态key)，删掉强转）； F3 是与之正交的 5 行外科手术（clear() 移出公开面，挪进 kernel internals 通道）； F4 不做自动拓扑排序——注册顺序在这个内核里是语义（decision 短路序 / pipe 变换序 / around 嵌套层次都由它决定）， 自动重排等于静默改行为，比警告更危险；正确姿势是 missing-required 提供 escalate-to-throw 选项 （对齐 assertCriticalDecisionHooks 的 fail-loud 哲学），slot 带 owner 后依赖图靠纯 tooling 生成。

议题 ③ 裁决 做 Slot API + clear() 收权 + escalate 选项；不做 capability 注入（留作三件套出现第三个消费者时的定向重构）、 不做 namespace、不做拓扑排序。迁移可渐进（物理 key 不变 → 运行时行为零变化，14 个文件分 PR 换）， 且恰好把 roadmap 原话——"跨 plugin key 仍需更强约束或 slot API"——落成实物。

VERDICT · 跨议题综合与取舍

总裁决：未来 2–3 个月只做三件事

六个议题放到一起排序，逻辑只有一条：确定性资损 > 现存 API 名不副实 > roadmap 挂名未完成项 > 证据工程 > 一切投机设计。 按这条线收敛出三个工作包：

1 · 内核信实性修复包

3 · 迁移证据工程

L1 seam 定向收口（lint + 冗余 import + R3 退避，合计约一天）作为前置，然后执行 7 条 spike 验证清单。

为什么第三：这是真正 gate 迁移决策的东西——把 roadmap 里"真实迁移证据"从口号变成 7 条可判定验收项。前两个工作包扫清的正是清单第 1、6 条的确定性障碍；升级 pi-ai 到 0.80.x 顺带走一次新 playbook。

同样重要：明确不做清单 不实现分支持久化（B/C′ 只写进设计文档并绑定触发条件——seam 已在，期权不过期）； 继续 defer sideQuestion controller 本体（真需求来时只是 60 行 recipe）； 不做 preset / 简化 facade / "轻量模式"（只做一小时的文档路标）； 不做 pi-ai 完整 re-export facade（定向收口足够）； 不做 hook 自动拓扑排序（注册顺序是语义，重排即改行为）； 不做 capability 注入重构（留作定向期权）。每一条"不做"都和"做"一样有明确理由与触发条件。

回到第一部分结语留下的那一课——"会话数据模型不必被迫线性"。深挖之后这一课的正确读法变了： 不是"去抄 pi-mono 的树"，而是确认自己的树形 seam 早已留好，然后把行权条件写清楚、把今天就存在的 footgun 用文档封掉。 借鉴的最高形式不是照搬对方的结构，而是借对方的存在，验证自己哪些期权已经免费持有、哪些承诺还没有兑现。 harness-pi 下一阶段的主题不是"补机制"，而是让已有机制的每一个承诺都名副其实——这正是三个工作包的公约数。

harness-pi 侧研究范围：packages/core/src（hook.ts / dispatcher.ts / session.ts / tool-executor.ts）、 packages/plugins/src（watchdog / repeated-call-guard / token-budget / controllers/lifecycle-restart 等）、 docs/00-01-03 架构与 hook 系统文档。

pi-mono 侧研究范围：git clone https://github.com/earendil-works/pi-mono（depth=1 快照）的 packages/agent/src（agent-loop.ts / agent.ts / types.ts / harness/*）与 packages/coding-agent/src/core/extensions。

第二部分研究方式：3 路并行深挖 sub-agent（会话数据模型与 sideQuestion / ctx.state 硬化与分层 / 迁移风险与 L1 seam）， 每路强制"先实读源码（结论挂 file:line）→ 具体失败场景 → ≥2 候选与权衡 → 立场明确的推荐"，全程只出方案不改代码； 跨议题优先级与"三个工作包 / 不做清单"为主线综合。L1 seam 的 churn 数据基于对 pi-mono 上游 git 历史的 deepen 实测。
